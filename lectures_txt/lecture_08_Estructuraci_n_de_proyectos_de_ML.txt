  Principios de ingeniería de software aplicados al ML
  Los
proyectos de machine learning
comparten muchas características con los sistemas de software tradicionales, pero también presentan desafíos únicos. Por eso, aplicar principios de ingeniería de software en su desarrollo resulta esencial para garantizar
soluciones sostenibles, colaborativas y escalables.
La planificación estructurada, la automatización de tareas, el control de versiones, la documentación y la validación de calidad son prácticas que deben estar presentes desde las primeras etapas del ciclo de vida del proyecto.
La
complejidad de los sistemas de ML
no radica únicamente en los algoritmos, sino en la interconexión de múltiples componentes: ingestión y validación de datos, preprocesamiento, entrenamiento, evaluación, almacenamiento de artefactos, visualización de resultados, entre otros.
Frente a este panorama, es fundamental adoptar una mirada sistémica, considerando no solo el modelo sino todo el flujo que lo rodea. Esto implica, diseñar estructuras predecibles, favorecer la modularidad, y utilizar herramientas que promuevan la
automatización, reproducibilidad y control.
En
entornos reales
, los sistemas de ML deben integrarse con servicios externos, respetar convenciones de seguridad, cumplir con estándares organizacionales y permitir auditoría en sus decisiones. Por eso, los principios de legibilidad, separación de responsabilidades, pruebas automatizadas, control de entornos y documentación clara dejan de ser opcionales: se convierten en los pilares de una solución lista para producción.

  El
objetivo pedagógico
de este bloque es fundamentar teóricamente la necesidad de estas prácticas y preparar el terreno para su implementación práctica en el caso integrador HealthCheck.
En él, el equipo técnico enfrentará un
proceso de refactorización estructural:
partiendo de un código desorganizado y difícil de mantener, incorporará progresivamente herramientas como Cookiecutter, Poetry, Makefile, Hydra y pre-commit hooks para transformar el sistema en un proyecto sólido, modular y profesional.

  Esta integración paso a paso permitirá observar con claridad cómo cada herramienta contribuye a los principios de la ingeniería de software, y cómo en conjunto logran un entorno de desarrollo más eficiente, controlado y preparado para escalar hacia producción.

  Estructura modular

  Adoptar una
estructura modular
significa dividir un proyecto en
unidades independientes y reutilizables
, cada una con una función específica dentro del sistema.
Esta organización favorece la mantenibilidad del código, facilita el trabajo en equipo y permite escalar los componentes sin romper funcionalidades existentes. En el contexto de ML, la modularidad implica separar de manera clara las etapas de
ingestión de datos, procesamiento, entrenamiento, evaluación y almacenamiento de resultados.

  En términos prácticos, una estructura modular típica incluye carpetas como:

  data/
→ almacenamiento y validación de datos
  features/
→ generación y transformación de características
  models/
→ definición, entrenamiento y evaluación de modelos
  utils/
→ funciones auxiliares y utilidades comunes
  notebooks/
→ exploraciones, experimentos o prototipos iniciales

  La
estructura modular
permite introducir conceptos fundamentales como
separación de responsabilidades, cohesión, bajo acoplamiento y reutilización de componentes.
Estos principios son la base para comprender más adelante herramientas y prácticas avanzadas como pipelines automatizados, testing unitario o despliegue por etapas.

  Cuando se trabaja con herramientas como
Cookiecutter
, esta estructura puede generarse automáticamente, asegurando que todos los proyectos sigan un patrón común y profesional.
De este modo,
se garantiza consistencia, facilidad de mantenimiento y un punto de partida sólido para incorporar nuevas herramientas.

  🧩En el caso HealthCheck
  La adopción de una estructura modular permitió establecer fronteras claras entre los componentes del sistema, transformando un conjunto disperso de scripts en un proyecto organizado y escalable.
Esa base estructural fue clave para integrar posteriormente herramientas como Poetry, Makefile, Hydra y pre-commit, consolidando un flujo de trabajo profesional y sostenible.

  Versionado de código y reproducibilidad

  ➡️Versionado de código
  El
versionado de código
es una práctica clave para cualquier proyecto de software, pero en ML adquiere un valor aún mayor por la cantidad de elementos que pueden afectar los resultados: datos, scripts, configuraciones, parámetros, versiones de librerías o incluso el hardware utilizado.
Usar un sistema como
Git
permite registrar cada cambio, colaborar de manera segura, y rastrear la evolución del proyecto de forma precisa, facilitando la coordinación entre equipos y la identificación de errores o regresiones.
  ➡️Reproducibilidad
  La
reproducibilidad,
por su parte, implica la capacidad de volver a ejecutar un pipeline bajo las mismas condiciones y obtener resultados equivalentes. Esto no solo es esencial para la validación científica y técnica, sino también para entornos productivos donde se necesita justificar el comportamiento de un modelo. Sin versionado y control de entorno, esta reproducibilidad es prácticamente imposible de garantizar.
Para lograrla, se recomienda versionar no solo el código fuente, sino también los datos, los modelos generados y los archivos de configuración y cualquier artefacto relevante para la ejecución.
Además, utilizar herramientas como
Poetry
(a través del archivo
pyproject.toml
) o
requirements.txt
, junto con entornos virtuales, ayuda a mantener la consistencia de dependencias entre equipos y entornos.

COmpletar desde aca!
  Cookiecutter
es una herramienta de generación de proyectos completos a partir de plantillas predefinidas. Su
objetivo principal
es automatizar la creación de estructuras estándar de proyectos, permitiendo iniciar nuevos desarrollos con una base sólida, consistente y reutilizable. A diferencia del clásico "copiar y pegar" de carpetas modelo, Cookiecutter permite parametrizar elementos del proyecto (nombre, autor, licencia, tipo de aplicación, etc.) y generar versiones adaptadas a diferentes contextos en pocos segundos.
En proyectos de machine learning, donde la
organización del repositorio
, la
consistencia entre módulos
y la
claridad de los puntos de entrada son críticas
,
Cookiecutter aporta numerosos beneficios.
Definir una plantilla con las carpetas esenciales
(
src/
,
data/
,
notebooks/
,
models/
, etc.), los
scripts base
(
train.py
,
predict.py
) y
archivos de configuración
(
README.md
,
.gitignore
,
pyproject.toml
) establece desde el inicio una
arquitectura coherente y profesional.
Esto reduce la carga cognitiva del equipo, previene errores estructurales y acelera la puesta en marcha de nuevos proyectos o experimentos.

  Ventajas:

  🟡Estandarización organizacional.
  Además, Cookiecutter facilita la estandarización organizacional: equipos de trabajo pueden definir una plantilla base oficial y compartirla a través de un repositorio remoto, permitiendo que todos los nuevos proyectos adopten la misma estructura, convenciones y herramientas desde el inicio.
Esta práctica mejora el mantenimiento a largo plazo, agiliza el onboarding de nuevos integrantes y habilita integraciones más simples con pipelines automatizados o CI/CD.
  🟡Flexibilidad
  Otra ventaja es la flexibilidad: las plantillas pueden incluir lógica condicional, carpetas opcionales y estructuras complejas que se activan o desactivan según las respuestas del usuario.
Esto permite crear plantillas adaptativas que sirven tanto para prototipos rápidos como para proyectos robustos destinados a producción, sin necesidad de múltiples versiones de base.
  🧩 En el caso HealthCheck
  Se generó una
plantilla Cookiecutter
personalizada que sirvió como punto de partida para reorganizar el proyecto. Esta plantilla incluyó todos los elementos necesarios para garantizar una base profesional desde cero, y permitió replicar rápidamente la estructura para futuras versiones o servicios derivados.
Gracias a esta estandarización, el equipo logró uniformar su flujo de trabajo, reducir errores iniciales y preparar el proyecto para incorporar de manera ordenada las siguientes herramientas del ecosistema de ingeniería de ML.

  Creación de una plantilla de proyecto ML

  Crear una plantilla de proyecto ML con Cookiecutter implica diseñar una estructura de carpetas y archivos pensada para cubrir el ciclo completo de vida del sistema: desde la adquisición de datos hasta el despliegue del modelo.
Esta estructura debe reflejar una
organización lógica, funcional y mantenible,
incluyendo espacios dedicados al código fuente, los scripts de entrenamiento y predicción, los datos de entrada, los artefactos de modelos, las pruebas automatizadas, la documentación y las configuraciones.
El proceso comienza con la creación de un
directorio
que actuará como plantilla.
Dentro de este se definen las carpetas y archivos base, por ejemplo:

  [codigo]
  {{cookiecutter.project_slug}}/
  │
  ├── src/ # Código fuente principal
  ├── data/ # Datos brutos y procesados
  ├── models/ # Artefactos de modelos entrenados
  ├── notebooks/ # Exploraciones o experimentos
  ├── tests/ # Pruebas automatizadas
  ├── README.md # Documentación inicial
  ├── pyproject.toml # Definición de dependencias (Poetry)
  ├── Makefile # Tareas automatizadas
  └── .gitignore # Archivos a excluir del control de versiones

  Las variables entre llaves ({{cookiecutter.project_slug}}, {{
cookiecutter.author
_name}}, etc.) serán reemplazadas automáticamente por los valores provistos al momento de crear un nuevo proyecto.
Estas variables se definen en el archivo
cookiecutter.json
, que puede incluir, por ejemplo:

  [codigo]
  {
  "project_name": "Nombre del proyecto",
  "project_slug": "nombre_proyecto",
  "author_name": "Equipo de Datos",
  "license": ["MIT", "Apache-2.0", "Proprietary"]
  }

  Una plantilla puede ser tan simple o compleja como el equipo lo necesite. Es posible incluir ejemplos de scripts básicos (
train.py
,
inference.py
), tests iniciales con
pytest
, configuraciones para linters, y hooks para pre-commit. Incluso se pueden definir plantillas con múltiples capas lógicas, como componentes para entrenamiento local y pipelines productivos. Esta capacidad permite alinear la estructura del código con las metodologías de trabajo del equipo.
Una vez construida la plantilla, se puede usar de forma local o compartir como un repositorio público o privado. Desde allí, otros usuarios podrán clonar e instanciar nuevos proyectos con un simple comando, obteniendo una estructura lista para trabajar sin errores de organización ni omisiones típicas. Esto ahorra tiempo, mejora la consistencia y garantiza una base profesional desde el inicio.

  🧩En HealthCheck
  La plantilla generada fue diseñada específicamente para proyectos de ML tabular, con estructuras comunes al ciclo de vida del modelo. Se incluyó un esqueleto base con código, datos, configuraciones, dependencias y scripts listos para ser completados en las fases siguientes del proyecto.

  Adaptación de la plantilla a distintos entornos (dev / prod)

  Una de las
mayores fortalezas
de
Cookiecutter
es su capacidad para generar estructuras adaptadas a diferentes entornos de trabajo.
En proyectos de ML, suele haber diferencias importantes entre el entorno de desarrollo (donde se prototipan modelos, se exploran datos y se prueba el código) y el entorno de producción (donde se ejecutan modelos en forma robusta, automatizada y monitoreada). Adaptar la plantilla a ambos escenarios desde el inicio permite evitar reestructuraciones posteriores costosas.
Para lograrlo, las plantillas pueden incluir
configuraciones condicionales o estructuras alternativas que se activan
según las decisiones del usuario al momento de crear el proyecto.
Por ejemplo, el archivo
cookiecutter.json
puede incorporar una pregunta como:

  [codigo]
  "use_ci": "¿Desea incluir integración continua (CI/CD)? [y/n]"

  Y en los archivos de la plantilla se puede definir lógica condicional como:

  [codigo]
  {% if cookiecutter.use_ci == 'y' %}
  .github/
  └── workflows/
  └── ci.yml
  
  {% endif %}

  De este modo, al instanciar un nuevo proyecto,
Cookiecutter
incluye o excluye automáticamente elementos específicos según el tipo de entorno:
Scripts de test o prototipado para desarrollo local.
Archivos de configuración de logging, Dockerfile o workflows de CI/CD para entornos productivos.
Esta capacidad automatiza la adaptación estructural y garantiza que cada entorno tenga solo los componentes que realmente necesita.
Otra posibilidad es definir variantes de configuración dentro del mismo proyecto, como archivos
config_dev.yaml
y
config_prod.yaml
, que serán utilizados por herramientas como Hydra o Makefile. De este modo, el mismo código puede adaptarse a distintos entornos con solo cambiar el archivo de configuración. Esta práctica favorece la portabilidad y reduce el riesgo de errores por diferencias entre entornos.
También se pueden incluir ramas de estructura específicas para distintos contextos: por ejemplo, una carpeta
infra/
que solo aparece en proyectos productivos, o una carpeta
research/
pensada para notebooks exploratorios en entornos de investigación. Estas decisiones deben estar alineadas con la estrategia general del equipo o la organización.

  The difference between Kirsten and Michelle should be noticeable. Kirsten is an accountable team member, and Michelle is not. Think about the unique impact this distinction would have on a remote team. As a remote team manager, you don’t always have the visibility or tools you need to keep tabs on Michelle.   🤖
COmpletar desde aca!
  Poetry es una herramienta que permite gestionar entornos virtuales y dependencias de forma integrada y moderna. Al iniciar un nuevo proyecto con
poetry init
, se genera automáticamente un archivo central llamado
pyproject.toml
, que actúa como el núcleo de configuración del entorno.
En este archivo se define toda la metadata del proyecto: nombre, versión, descripción, autoría y, fundamentalmente, las librerías necesarias para ejecutar el código. Este archivo reemplaza al tradicional
setup.py
y permite mantener el proyecto alineado con los estándares modernos del ecosistema Python.

  Ejemplo básico de un
pyproject.toml
generado por Poetry:

  [codigo]
  [tool.poetry]
  name = "healthcheck"
  version = "0.1.0"
  description = "Sistema de evaluación de riesgos sanitarios"
  authors = ["Equipo de Datos equipo@healthcheck.com
  "]
  
  [tool.poetry.dependencies]
  python = "^3.10"
  pandas = "^2.2.0"
  scikit-learn = "^1.5.0"
  
  [tool.poetry.dev-dependencies]
  pytest = "^8.0.0"
  black = "^24.3.0"

  Además de
pyproject.toml
, Poetry crea un archivo complementario llamado
poetry.lock
. Este archivo no debe editarse manualmente: su función es registrar de forma precisa las versiones exactas de todas las dependencias, incluyendo las subdependencias que cada paquete instala automáticamente. Gracias a este lockfile, cualquier persona puede clonar el repositorio, ejecutar
poetry install
y tener el mismo entorno reproducido byte a byte, sin depender del entorno local ni de la máquina.
Cuando se ejecuta cualquier comando de instalación o actualización, Poetry también crea automáticamente un entorno virtual dedicado al proyecto, sin necesidad de herramientas adicionales como
virtualenv
. Esto garantiza el aislamiento completo entre proyectos, evita conflictos de versiones y asegura que las ejecuciones sean consistentes entre distintos desarrolladores, entornos o sistemas operativos.

  Comparado con el enfoque clásico basado en
pip
+
requirements.txt
, Poetry ofrece una solución más completa y segura. Mientras que
pip
instala paquetes sin bloquear sus subdependencias por defecto, Poetry asegura que todas las versiones estén congeladas en el lockfile. Además, evita la necesidad de mantener manualmente un archivo de requerimientos, y permite declarar entornos de desarrollo y producción de forma separada.

  🧩En nuestro caso de uso
  En el caso HealthCheck, esta estructura fue adoptada desde el inicio del rediseño del proyecto.
pyproject.toml
concentró las definiciones del entorno y permitió establecer dependencias mínimas claras, mientras que
poetry.lock
garantizó que las versiones utilizadas en entrenamiento y testing fueran siempre idénticas entre el entorno local y el pipeline CI/CD.

  La gestión de librerías con Poetry se realiza a través de una interfaz de comandos intuitiva que permite instalar, actualizar o eliminar dependencias sin editar manualmente ningún archivo. De este modo, la configuración del entorno se mantiene centralizada, coherente y trazable.

  👩🏽‍💻 Para instalar una nueva librería:
  Basta con ejecutar
poetry add nombre_paquete
, y Poetry se encargará de registrar la dependencia en
pyproject.toml
, resolver sus versiones compatibles, y actualizar el archivo
poetry.lock
. Si la dependencia es solo para desarrollo (por ejemplo,
pytest
), se agrega con la bandera
--dev
.
  🧩En nuestro caso de uso:
  En el flujo de trabajo de HealthCheck, estas capacidades se integraron al Makefile, facilitando comandos como
make install
o
make update
para reproducir o actualizar el entorno sin errores manuales. También se utilizó la exportación para generar archivos
requirements.txt
compatibles con herramientas de análisis externo o servicios en la nube que aún no reconocen
pyproject.toml
.
  🔁Actualizar paquetes también es simple:
  poetry update
revisa las versiones de cada dependencia según las restricciones definidas y genera un nuevo lockfile con las versiones más recientes compatibles. Además, se puede actualizar un paquete específico sin afectar el resto del entorno.
Cuando se elimina una librería,
poetry remove
se encarga de limpiar ambas fuentes (
pyproject.toml
y
poetry.lock
) de forma segura.
  ➡️Para compartir o desplegar el entorno en otros contextos
  Por ejemplo, servidores, contenedores o notebooks externos, Poetry permite exportar todas las dependencias a un archivo
requirements.txt
compatible con
pip
, utilizando el comando
poetry export --without-hashes > requirements.txt
. Esta funcionalidad permite integrar proyectos basados en Poetry con sistemas que aún requieren los formatos clásicos, facilitando la interoperabilidad.
  📊En comparación:
  En comparación con el enfoque
pip freeze > requirements.txt
, Poetry ofrece mayor control y trazabilidad. Mientras que
pip freeze
registra todas las librerías instaladas en el entorno —incluso las que el proyecto no necesita directamente—,
poetry export
permite generar una lista limpia basada únicamente en las dependencias reales del proyecto, evitando inflar innecesariamente el entorno.

Automatización de tareas con Makefile [blocks]
================================================================================
  Estructura y sintaxis básica de un Makefile
  The difference between Kirsten and Michelle should be noticeable. Kirsten is an accountable team member, and Michelle is not. Think about the unique impact this distinction would have on a remote team. As a remote team manager, you don’t always have the visibility or tools you need to keep tabs on Michelle. It’s much easier for Michelle to ignore a direct message or email from you than it is for her to ignore a knock on her office door. A lack of follow-up and follow-through may breed distrust, and even resentment, between you and Michelle, or Michelle and her other team members.

  🤖
COmpletar desde aca!
  Makefile
es una herramienta clásica del ecosistema Unix que permite automatizar tareas repetitivas mediante reglas declarativas. Aunque fue concebida originalmente para compilación de código en C/C++, su simplicidad y flexibilidad la convirtieron en una herramienta ampliamente utilizada en proyectos de cualquier lenguaje, incluyendo Python y machine learning. En proyectos de ML, Makefile permite simplificar comandos complejos, estandarizar flujos de trabajo y reducir errores humanos.
La estructura de un archivo
Makefile
se basa en “targets” o tareas que el usuario puede invocar con
make nombre_de_tarea
. Cada target define un nombre (como
train
o
test
), una lista opcional de dependencias, y una o más líneas de comandos que se ejecutan cuando se invoca el target. Es fundamental respetar la indentación con
tabulaciones reales
, ya que el formato no acepta espacios como sustituto.

  Un ejemplo básico de Makefile puede ser:

  [codigo]
  install:
  	poetry install
  
  train:
  	poetry run python src/train_model.py

  Cada bloque define una tarea con nombre y sus instrucciones. Además, es posible encadenar tareas, por ejemplo definiendo un target
all
que llame a
install
,
lint
,
test
y
train
. También se pueden agregar comentarios y variables reutilizables, lo que convierte al Makefile en una especie de guion automatizado del proyecto.

  🧩En nuestro caso de uso
  En
HealthCheck
, el equipo incorporó un Makefile en la raíz del repositorio como punto de entrada estandarizado para todos los integrantes. Esto permitió ejecutar tareas críticas con comandos simples como
make train
, evitando recordar rutas largas o dependencias específicas. El Makefile se convirtió en una herramienta esencial para la fluidez del trabajo diario y la integración futura con CI/CD.

  Definición de tareas comunes: make train, make lint, make test

  Uno de los principales beneficios del uso de Makefile en proyectos de ML es la
capacidad de encapsular tareas frecuentes y darles nombres claros y reutilizables.
Esto permite estandarizar procesos que, de otro modo, requerirían ejecutar secuencias de comandos complejos o recordar configuraciones específicas del entorno.
Entre las más comunes se encuentran la ejecución del entrenamiento (
make train
), la validación de estilo de código (
make lint
) y la ejecución de tests automatizados (
make test
). Cada una de estas tareas puede representar varios comandos complejos que se simplifican en una única instrucción estandarizada.
Por ejemplo, el target
make train
puede encapsular la ejecución del script de entrenamiento del modelo, utilizando Poetry como entorno de ejecución seguro. El comando correspondiente sería algo como
poetry run python src/train_
model.py
. Del mismo modo,
make lint
puede ejecutar
black
y
flake8
en la carpeta
src/
para verificar estilo y errores estáticos. Estas validaciones permiten mantener la calidad del código sin depender de acciones manuales.
La tarea
make test
suele invocar
pytest
para ejecutar pruebas unitarias o de integración. Es posible configurar este target para mostrar cobertura, detener la ejecución ante errores o incluso generar reportes HTML. Además, se pueden agregar otros targets útiles como
make clean
para eliminar archivos temporales,
make docs
para generar documentación, o
make format
para aplicar formatters automáticamente.

  Veamos un ejemplo

  A continuación, se muestra un ejemplo típico de
Makefile
para un proyecto de ML gestionado con Poetry:

  [codigo]
  # Entrenamiento del modelo
  train:
      poetry run python src/train_model.py
  
  # Validación de estilo de código
  lint:
      poetry run black src/ && poetry run flake8 src/
  
  # Ejecución de tests automatizados
  test:
      poetry run pytest -v --cov=src --cov-report=term-missing
  
  # Limpieza de archivos temporales
  clean:
      rm -rf __pycache__ .pytest_cache .mypy_cache
  
  # Formateo automático de código
  format:
      poetry run black src/

  La
ventaja
de definir estas tareas es que cualquier persona del equipo puede ejecutar acciones complejas con comandos simples, sin preocuparse por rutas, entornos o flags particulares. Esto reduce significativamente los errores humanos y promueve una cultura de automatización y consistencia.

  🧩En nuestro caso de uso
  En
HealthCheck
, se definieron todos estos targets como parte de la transición a buenas prácticas de desarrollo. Los comandos make train, make lint y make test fueron integrados en la rutina diaria del equipo, y luego incorporados también en los workflows de GitHub Actions. Esto permitió asegurar que el mismo código que se probaba localmente funcionara exactamente igual en los entornos automatizados.

  Ejecución de flujos automatizados para CI/CD local

  Además de facilitar la ejecución manual de tareas,
Makefile
permite componer
flujos de trabajo completos que simulan pipelines CI/CD en el entorno local.
Esto resulta particularmente útil en proyectos de ML donde se deben encadenar múltiples pasos —como validación de datos, entrenamiento, testing, formateo de código, generación de artefactos— antes de aceptar un cambio o desplegar un modelo.
Un target habitual para este fin es
make all
, que puede ejecutar en secuencia tareas como
lint
,
test
,
train
y
docs
. Esto permite validar que el sistema esté en condiciones de integrarse o desplegarse sin errores, replicando localmente lo que luego ocurrirá en un workflow CI. También se pueden crear targets de validación previos a cada commit (
make validate
) o integrarlos con hooks automáticos como pre-commit.
Makefile
también puede servir como interfaz de orquestación para tareas más complejas. Por ejemplo, se pueden definir targets para lanzar contenedores Docker, sincronizar archivos con S3, ejecutar scripts con parámetros específicos, o disparar notebooks automatizados. Esta flexibilidad convierte al Makefile en una herramienta intermedia entre el código fuente y la automatización full de CI/CD.
Aunque
GitHub Actions
o
Jenkins
serán finalmente quienes ejecuten los pipelines en producción, tener estos flujos ya definidos y testeados localmente con Makefile acelera su adopción, simplifica la depuración y garantiza que no haya sorpresas al migrar hacia automatización completa.

  🧩En nuestro caso de uso
  En
HealthCheck
, se utilizó
make all
como paso previo obligatorio antes de cada push. Este target ejecutaba validaciones, tests y entrenamiento, asegurando que el código ingresara al repositorio solo si superaba todas las verificaciones. Esta estrategia evitó errores en producción y mejoró la calidad del sistema de forma progresiva.

Gestión de configuraciones con Hydra [blocks]
================================================================================
  Uso de archivos YAML para manejar parámetros dinámicos
  The difference between Kirsten and Michelle should be noticeable. Kirsten is an accountable team member, and Michelle is not. Think about the unique impact this distinction would have on a remote team. As a remote team manager, you don’t always have the visibility or tools you need to keep tabs on Michelle. It’s much easier for Michelle to ignore a direct message or email from you than it is for her to ignore a knock on her office door. A lack of follow-up and follow-through may breed distrust, and even resentment, between you and Michelle, or Michelle and her other team members.

  🤖
COmpletar desde aca!
  En proyectos de machine learning, los parámetros se multiplican rápidamente: rutas a los datos, hiperparámetros del modelo, flags de ejecución, nombres de salida, configuraciones por entorno, entre otros.
Manejar todos estos valores embebidos en el código se vuelve inmanejable y dificulta tanto el mantenimiento como la reproducibilidad. Hydra es una herramienta diseñada específicamente para abordar este problema mediante el uso de archivos YAML jerárquicos y dinámicos.
Hydra organiza las configuraciones en archivos
.yaml
, cada uno correspondiente a una categoría específica (por ejemplo,
model.yaml
,
paths.yaml
,
train.yaml
).
Estos archivos se almacenan en una carpeta común —por convención,
/configs
— y pueden combinarse, heredarse o sobrescribirse dinámicamente al momento de ejecutar el código.

  Por ejemplo, una estructura típica podría verse así:

  [codigo]
  configs/
  │
  ├── config.yaml        # Configuración principal
  ├── model/
  │   ├── rf.yaml        # RandomForest
  │   └── xgb.yaml       # XGBoost
  ├── paths/
  │   ├── local.yaml     # Rutas locales
  │   └── prod.yaml      # Rutas en producción
  └── train/
      ├── default.yaml
      └── fast.yaml

  Los archivos YAML utilizados por Hydra se almacenan típicamente en una carpeta
/configs
, y pueden organizarse jerárquicamente para reflejar la estructura del sistema. Por ejemplo, un archivo
config.yaml
principal puede incluir referencias a otros archivos mediante claves como
defaults: - model: rf - paths: local
, lo que permite construir configuraciones complejas sin duplicar información. Esta lógica no solo mejora la organización, sino que evita errores y facilita la trazabilidad.

  🧩Un ejemplo concreto
  Un ejemplo concreto de uso podría incluir un archivo
model.yaml
con los hiperparámetros de un RandomForest, un archivo
paths.yaml
con rutas a los datos de entrada, salida y artefactos, y un archivo
pipeline.yaml
que indique los pasos a ejecutar y sus configuraciones específicas. Al ejecutar un script, se puede cambiar cualquiera de estos elementos fácilmente sin tocar el código fuente, simplemente modificando el YAML o pasando argumentos por línea de comandos.
  🧩En nuestro caso de uso:
  En el proyecto
HealthCheck
, esta organización permitió definir configuraciones separadas para el entrenamiento, la predicción y el monitoreo del modelo, incluyendo hiperparámetros, rutas de entrada y salida, y flags de logging. Al centralizar estos parámetros, el equipo ganó control, flexibilidad y capacidad de auditar cada ejecución sin depender de comentarios o documentación externa.

  Integración con scripts de entrenamiento y predicción

  La integración de Hydra en los scripts de ML se realiza mediante el decorador
@hydra.main
, que reemplaza la típica lectura manual de argumentos o archivos de configuración. Este decorador transforma el script en un componente configurable, capaz de recibir un conjunto completo de parámetros desde archivos YAML o argumentos de línea. Esto permite desacoplar la lógica del código de los valores específicos de ejecución, haciendo que los scripts sean más reutilizables, testeables y portables.

  Por ejemplo, un script
train_model.py
puede incorporar la configuración mediante:

  [codigo]
  @hydra.main(config_path="configs", config_name="config")
  def train(cfg):
      model_type = cfg.model.type
      n_estimators = cfg.model.n_estimators
      data_path = cfg.paths.train_data

  Esta estructura permite acceder a cualquier parámetro definido en los archivos YAML mediante notación de punto (
cfg.model.type
,
cfg.paths.output_dir
, etc.), con validación automática de tipos y existencia de claves. También permite anidar configuraciones, definir defaults y aplicar validaciones más complejas a través de librerías como OmegaConf (que Hydra utiliza internamente).
Los mismos principios se aplican a los scripts de predicción, evaluación o monitoreo. Cada script recibe su configuración desde un archivo YAML y puede ser ejecutado con distintas variantes pasando argumentos como
python predict.py paths.data=path/to/input.csv model.checkpoint=path/to/model.pkl
. Esta flexibilidad permite crear flujos adaptables a distintos entornos, sin tocar una línea de código.

  🧩En nuestro caso de uso:
  En
HealthCheck
, los scripts
train_model.py
,
predict.py
y
model_monitoring.py
fueron integrados con Hydra. Esto permitió modificar hiperparámetros, cambiar rutas, activar modos de depuración o seleccionar diferentes modelos simplemente ajustando los YAML, sin riesgo de errores por cambios manuales en el código. Además, Hydra generó una carpeta por ejecución con logs y configuraciones utilizadas, aportando trazabilidad completa.

Calidad, documentación y pre-commit hooks [blocks]
================================================================================
  Formateo y linting con Black, Flake8, Isort e Interrogate
  The difference between Kirsten and Michelle should be noticeable. Kirsten is an accountable team member, and Michelle is not. Think about the unique impact this distinction would have on a remote team. As a remote team manager, you don’t always have the visibility or tools you need to keep tabs on Michelle. It’s much easier for Michelle to ignore a direct message or email from you than it is for her to ignore a knock on her office door. A lack of follow-up and follow-through may breed distrust, and even resentment, between you and Michelle, or Michelle and her other team members.

  🤖
COmpletar desde aca!
  Mantener la calidad del código en proyectos de ML es una tarea fundamental, especialmente cuando múltiples personas colaboran en el mismo repositorio o cuando el sistema debe evolucionar a lo largo del tiempo. Herramientas de formateo y linting como
Black, Flake8, Isort e Interrogate
permiten automatizar estándares de estilo, detectar errores potenciales y verificar la completitud de la documentación sin intervención manual. Estas herramientas no solo mejoran la legibilidad del código, sino que reducen errores y elevan el nivel profesional del desarrollo.

  ⚫Black
  Es un
formateador de código automático
que aplica reglas de estilo predefinidas para asegurar consistencia entre archivos. A diferencia de otros linters, no intenta sugerir estilos alternativos: simplemente reescribe el código para que cumpla un formato estricto. Esto elimina discusiones sobre estilos y asegura que todo el equipo trabaje con el mismo criterio. Su uso básico (
black src/
) reestructura todo el código fuente de forma inmediata y confiable.
  🔎Flake8
  Actúa como un
validador sintáctico
que analiza el código en busca de errores de lógica, convenciones de estilo (PEP8), variables no utilizadas, funciones excesivamente complejas o nombres poco descriptivos. Se puede complementar con plugins que agregan chequeos adicionales. Isort, por su parte, organiza automáticamente las importaciones según una jerarquía definida (standard library, third-party, local imports), lo cual mejora la limpieza del código y previene conflictos.
  📝Interrogate
  Evalúa el nivel de documentación del proyecto analizando cuántas clases, funciones o métodos tienen docstrings.
Aporta una métrica objetiva de cobertura documental que puede ser utilizada como estándar mínimo del equipo. Por ejemplo, se puede definir que al menos el 70% de las funciones estén documentadas, y fallar el build si no se cumple. Esta verificación se vuelve clave cuando los proyectos deben ser mantenibles, compartidos o expuestos a usuarios externos.

  🧩En
HealthCheck
, todas estas herramientas fueron configuradas en el entorno del proyecto y ejecutadas automáticamente mediante pre-commits y tareas en el Makefile. Su aplicación sistemática elevó la calidad general del código y permitió detectar errores antes de que llegaran al repositorio, mejorando la mantenibilidad del sistema a medida que crecía.

  Integración de pre-commit hooks en Git

  Los
pre-commit hooks
son scripts que se ejecutan automáticamente antes de confirmar un cambio (
git commit
). Su principal
objetivo
es evitar que se suba al repositorio código con errores de estilo, problemas sintácticos o carente de documentación. Al integrar herramientas como Black, Flake8, Isort o Interrogate en estos hooks, se fuerza al equipo a cumplir ciertos estándares mínimos antes de cada confirmación, lo que mejora la salud general del proyecto sin esfuerzo adicional.

  La integración de pre-commit se realiza mediante la herramienta pre-commit:
  Permite definir una serie de validaciones en el archivo
.pre-commit-config.yaml
. Cada hook se especifica con un repositorio de origen, una versión (rev) y una lista de acciones (
id
) a ejecutar. Por ejemplo, se puede configurar que se corran
black
,
flake8
y
isort
sobre los archivos modificados antes de cada commit, y que se bloquee la operación si alguno de ellos falla.
  🧩En nuestro caso de uso
  En
HealthCheck
, la integración de pre-commit fue clave para institucionalizar los estándares de calidad. Se configuraron hooks para Black, Isort, Flake8 e Interrogate, y se exigió su cumplimiento antes de aceptar cualquier nueva contribución. Esto redujo errores de integración, mejoró la uniformidad del código y facilitó la colaboración entre integrantes con diferentes niveles de experiencia.
  Una vez definida la configuración, el hook se instala con el comando pre-commit install:
  Lo asocia al repositorio Git actual. A partir de ese momento, cada
git commit
pasará por una serie de controles automáticos. Esta práctica reduce la necesidad de revisiones manuales y asegura que todo el código confirmado cumpla con las normas básicas del equipo. Además, los hooks pueden ejecutarse manualmente sobre todo el proyecto con
pre-commit run --all-files
.
  Este mecanismo también permite:
  Extender los chequeos a validaciones personalizadas, como verificación de tamaño de archivos, detección de credenciales expuestas, análisis de complejidad ciclomática, o ejecución de tests básicos. Es una forma efectiva de aplicar políticas de calidad sin depender de la disciplina individual o de procesos externos de revisión.

  Generación automática de documentación con pdoc

  Documentar un proyecto de ML
no solo implica explicar cómo usarlo, sino también detallar cómo está estructurado, cómo se comportan sus componentes internos y cuáles son sus dependencias. Para automatizar este proceso y mantener la documentación alineada con el código, se pueden usar herramientas como
pdoc
, que generan documentación en formato HTML directamente a partir de los docstrings de las funciones, clases y módulos del proyecto.

  pdoc
  Recorre el código fuente y crea páginas navegables que explican qué hace cada módulo, qué argumentos reciben las funciones, qué retornan, y cuál es su estructura jerárquica.
Su principal
ventaja
es que la documentación se mantiene sincronizada con el código: cualquier cambio en el docstring se refleja automáticamente en el sitio generado, eliminando duplicaciones o errores en la documentación técnica.
  🧩En nuestro caso de uso:
  En
HealthCheck
, se integró pdoc en el flujo de desarrollo para generar documentación técnica de los módulos
train_model.py
,
predict.py
y
utils/
. Esto permitió crear un recurso navegable donde se detallaba la lógica del sistema, accesible para el equipo técnico y futuros mantenedores. También se utilizó como punto de partida para la documentación más amplia del sistema, incluyendo ejemplos y especificaciones del modelo.
  🛠️Instalación
  La
instalación
se realiza con
poetry add --dev pdoc
, y su ejecución básica puede ser tan simple como
pdoc src --html --output-dir docs
.
Este comando
genera un sitio estático con toda la documentación del proyecto,
que puede versionarse junto al código o incluso publicarse automáticamente en plataformas como GitHub Pages. También
permite personalizar el estilo
, agregar portadas, o incluir documentación adicional no generada automáticamente.
  📌Importante:
  Esta práctica no reemplaza la documentación funcional o de usuario
, pero sí aporta una referencia técnica valiosa para desarrolladores nuevos, revisores o usuarios avanzados. Además, sirve como insumo para revisiones de código, debugging o auditorías externas, al mostrar claramente qué hace cada componente y bajo qué condiciones.
